# M1 — Game Engine MCD/MLD Specification

**Sprint 2 — Task 10**
**Status:** Proposed by M1 — awaiting database integration review with M5
**Scope:** Five new models, reusing the existing `User` and `Room` models.

## 1. Existing Models (No Changes Requested)

| Model | Primary Key | Owner |
|---|---|---|
| User | `id` — INT | M2 |
| Room | `id` — UUID | M4 |

`RoomPlayer` continues to represent current room membership. It must not replace the Game Engine's fixed participant roster.

## 2. New Model: Game

Represents one game session from initialization to its final outcome.

| Field | Type | Constraint |
|---|---|---|
| `id` | UUID | PK, generated by M1 |
| `roomId` | UUID | FK → Room.id, UNIQUE |
| `phase` | GamePhase | NOT NULL |
| `currentRoundNumber` | INT | NOT NULL, starts at 1 |
| `secretWord` | STRING | NOT NULL, private |
| `phaseEndsAt` | DATETIME | Nullable |
| `winner` | GameWinner | Nullable |
| `terminationReason` | TerminationReason | Nullable |
| `startedAt` | DATETIME | NOT NULL |
| `endedAt` | DATETIME | Nullable |

**Enums:**

- `GamePhase`: ROLE_ASSIGNMENT, CLUE_SUBMISSION, DISCUSSION, VOTING, FINISHED, TERMINATED
- `GameWinner`: SPY, DETECTIVES
- `TerminationReason`: SPY_DEPARTED, INSUFFICIENT_PLAYERS

**Constraints:**

- One game per room, enforced by `UNIQUE(roomId)`.
- A normal finished game has a winner and an `endedAt` timestamp.
- A terminated game has no winner, has a termination reason and an `endedAt` timestamp.
- Active games have no final winner or `endedAt` timestamp.
- `phaseEndsAt` is required for timed gameplay phases.
- Secret-word access is restricted by the Game Engine, never by frontend hiding.

## 3. New Model: GamePlayer

Represents a participant belonging to a game.

| Field | Type | Constraint |
|---|---|---|
| `id` | INT | PK, auto-increment |
| `gameId` | UUID | FK → Game.id, NOT NULL |
| `userId` | INT | FK → User.id, NOT NULL |
| `role` | GameRole | NOT NULL |
| `participationStatus` | ParticipationStatus | NOT NULL |
| `connectionStatus` | ConnectionStatus | NOT NULL |

**Enums:**

- `GameRole`: SPY, DETECTIVE
- `ParticipationStatus`: ACTIVE, ELIMINATED, DEPARTED
- `ConnectionStatus`: CONNECTED, DISCONNECTED

**Constraints:**

- `UNIQUE(gameId, userId)` prevents adding the same user twice to one game.
- Each game begins with exactly one Spy and 2–7 Detectives.
- A game starts with 3–8 participants.
- Roles never change during a game.
- Participation is preserved even if M4 removes the player's RoomPlayer membership.
- Gameplay eligibility is validated by M1.

## 4. New Model: GameRound

Represents a numbered round belonging to a game.

| Field | Type | Constraint |
|---|---|---|
| `id` | INT | PK, auto-increment |
| `gameId` | UUID | FK → Game.id, NOT NULL |
| `number` | INT | NOT NULL, starts at 1 |
| `outcome` | RoundOutcome | Nullable until resolution |
| `eliminatedGamePlayerId` | INT | Nullable FK → GamePlayer.id |
| `resolvedAt` | DATETIME | Nullable until resolution |

**Enum:**

- `RoundOutcome`: ELIMINATED, TIE, NO_VOTES

**Constraints:**

- `UNIQUE(gameId, number)` prevents duplicate round numbers.
- Every round belongs to exactly one game.
- Only a player belonging to the same game can be eliminated.
- Ties and no-vote outcomes do not eliminate anyone.
- Round resolution is performed once.
- The active `Game.currentRoundNumber` must match the current GameRound.

## 5. New Model: Clue

Represents one accepted clue submitted during a round.

| Field | Type | Constraint |
|---|---|---|
| `id` | INT | PK, auto-increment |
| `roundId` | INT | FK → GameRound.id, NOT NULL |
| `authorGamePlayerId` | INT | FK → GamePlayer.id, NOT NULL |
| `text` | STRING (max 100) | NOT NULL |
| `normalizedText` | STRING (max 100) | NOT NULL |
| `submittedAt` | DATETIME | NOT NULL |

**Constraints:**

- `UNIQUE(roundId, authorGamePlayerId)` allows one accepted clue per player per round.
- `UNIQUE(roundId, normalizedText)` prevents duplicate clues within one round.
- `normalizedText` stores the trimmed, case-normalized clue for comparison.
- Empty clues, expired submissions and ineligible authors are rejected by M1.
- The author must belong to the game associated with the round.
- A clue from an earlier round may be reused in a later round.

## 6. New Model: Vote

Represents one accepted vote from a player during a round.

| Field | Type | Constraint |
|---|---|---|
| `id` | INT | PK, auto-increment |
| `roundId` | INT | FK → GameRound.id, NOT NULL |
| `voterGamePlayerId` | INT | FK → GamePlayer.id, NOT NULL |
| `targetGamePlayerId` | INT | FK → GamePlayer.id, NOT NULL |
| `submittedAt` | DATETIME | NOT NULL |

**Constraints:**

- `UNIQUE(roundId, voterGamePlayerId)` allows one accepted vote per voter per round.
- Voter and target must belong to the same game as the round.
- Only eligible active players may vote.
- Vote targets must be active, eligible game participants.
- Self-voting is allowed.
- Late and duplicate votes are rejected.
- Voting results are calculated by M1 at round resolution.

## 7. Relationship Summary

| Relationship | Cardinality |
|---|---|
| Room → Game | 1 → 0..1 |
| User → GamePlayer | 1 → 0..N |
| Game → GamePlayer | 1 → 3..8 at initialization |
| Game → GameRound | 1 → 1..N |
| GameRound → Clue | 1 → 0..N |
| GameRound → Vote | 1 → 0..N |
| GamePlayer → Clue | 1 → 0..N |
| GamePlayer → Vote (voter) | 1 → 0..N |
| GamePlayer → Vote (target) | 1 → 0..N |

## 8. Simplifications

- No separate Word table: the word list is maintained in backend code and the selected word is stored in Game.
- No separate GameResult table: terminal status, winner, reason and end timestamp are stored in Game.
- No XP, leaderboard, progression or player-facing match-history models.
- No duplication of user profile or room membership information.
- M4 receives only the agreed minimal final-result payload.

## 9. Data Integrity and Deletion

- M1 creates game data and participant records consistently, ideally within a database transaction.
- M1 ensures that accepted clues and votes reference players belonging to the corresponding game.
- Database uniqueness constraints protect against repeated submissions and votes.
- Active games must not be deleted while gameplay is running.
- Room deletion must not destroy an unfinalized game.
- Recommended starting policy: restrict room deletion while dependent game data exists; agree on an explicit post-game cleanup sequence.
- Exact foreign-key deletion rules and transaction implementation are reviewed with M5 and M4.
