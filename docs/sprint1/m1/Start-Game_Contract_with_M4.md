# M1 — Start-Game Contract with M4

**Sprint 1 — Task 2: Game Engine & Rooms Integration**

**Status:** Proposed by M1 — awaiting M4 confirmation.

### Purpose and ownership

- M4 receives the host's Start Game action and validates room existence, host authorization, room membership, and room availability.
- M4 passes a trusted snapshot of participating user IDs to M1.
- M1 validates the game-start conditions, creates the game, and initializes its first phase.
- M4 manages room restrictions after a successful start.
- M1 manages all gameplay behavior after initialization.

### Start-Game Request

**Proposed operation:** `startGame`

**Caller:** M4 (Rooms)

**Receiver:** M1 (Game Engine)

**Minimum request:**

```json
{
  "roomId": "room-123",
  "participantIds": [
    "user-101",
    "user-102",
    "user-103"
  ]
}
```

- `roomId`: Identifier of the room starting a game.
- `participantIds`: Fixed snapshot of the players participating in the game.
- Player identifiers must use M2's agreed user ID type.
- The host's identity does not need to be included as a separate field; M4 validates host authorization before calling M1.
- The request must originate from trusted backend integration, not an arbitrary client-provided participant list.

### M1 Start Validation

M1 rejects the request when:

- `roomId` or `participantIds` is missing or invalid.
- Fewer than 3 or more than 8 participants are supplied.
- Duplicate participant IDs exist.
- Another active game already exists for the same room.
- Game initialization fails.

If validation succeeds, M1:

- Creates a unique game identifier.
- Records the fixed participant roster.
- Randomly assigns exactly one Spy and the remaining Detective roles.
- Randomly selects one secret word from the predefined backend word list.
- Initializes Round 1.
- Enters `CLUE_SUBMISSION` with a server-controlled 60-second deadline.
- Makes private, role-specific game information available to each authenticated participant.

### Successful Start Response

**Example:**

```json
{
  "gameId": "game-456",
  "roomId": "room-123",
  "phase": "CLUE_SUBMISSION",
  "roundNumber": 1,
  "phaseEndsAt": "2026-11-02T12:01:00Z"
}
```
- `ROLE_ASSIGNMENT` is executed automatically before M1 returns a successful start response. Therefore, the response reports `CLUE_SUBMISSION` as the current phase. No additional timer or player acknowledgment is required.

- `gameId`: Identifier created by M1.
- `roomId`: Room associated with the game.
- `phase`: Initial gameplay phase.
- `roundNumber`: Starts at 1.
- `phaseEndsAt`: Authoritative UTC deadline generated by M1.

The response must not expose secret roles or the secret word.

After successful initialization:

- M4 marks the room as having an active game and prevents new players from joining.
- M3 receives the information needed to display the current gameplay phase.
- Each participant receives their own authorized role information privately.
- M1 prevents another active game from being created for the same room.

### Error Response

**Proposed common error format:**

```json
{
  "code": "INVALID_PLAYER_COUNT",
  "message": "A game requires 3 to 8 players."
}
```

**M1 errors**

| Error code | Cause |
|---|---|
| `INVALID_START_REQUEST` | Missing or malformed input |
| `INVALID_PLAYER_COUNT` | Player count outside 3–8 |
| `DUPLICATE_PLAYERS` | Repeated user ID |
| `GAME_ALREADY_ACTIVE` | Room already has an active game |
| `GAME_INITIALIZATION_FAILED` | Game creation could not complete |

**M4 errors**

| Error code | Cause |
|---|---|
| `ROOM_NOT_FOUND` | Room does not exist |
| `NOT_ROOM_HOST` | Requester is not the host |
| `ROOM_NOT_AVAILABLE` | Room cannot start a game |
| `ROOM_MEMBERSHIP_INVALID` | Participant list does not match valid room membership |

- M4 validates its room-specific conditions before invoking M1.
- If M1 rejects the request, M4 returns the appropriate error to the requesting client.
- A rejected start must not create a partially playable game or lock the room permanently.
- Error identifiers are proposed; exact codes and any HTTP status mappings must be agreed with M4.

### Start Consistency

- A room must have at most one active game.
- Simultaneous Start Game requests must not create duplicate games.
- M4 must not announce a successful start until M1 confirms initialization.
- The two modules must agree how room locking and game initialization remain consistent if an error occurs.
- M1 must not broadcast another player's private role or secret word in a room-wide event.

### Module Responsibilities

- **M1:** Game-start validation, unique game creation, roles, secret word, first round, initial deadline, and game metadata.
- **M4:** Room and host validation, authoritative room roster, Start Game entry point, room locking, and client-facing room errors.
- **M2:** Authenticated user identity.
- **M3:** Start Game interface, initial game display, and private role display.
- **M5:** Security guidance for authenticated backend and realtime communication.
